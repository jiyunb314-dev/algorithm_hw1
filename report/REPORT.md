| 검사 | 내용 |
| --- | --- |

| C · Python 대조 | 같은 배열 · 같은 씨앗으로 두 구현을 돌려 비교 · 섞기 횟수까지 같은지 `diff`로 본다 |

**테스트가 실제로 잡는지도 확인했다(변이 테스트).** 통과하는 테스트는 아무것도 증명하지
않으므로, 구현을 일부러 바꿔 보고 실패하는지 보았다.

| 바꾼 곳 | 결과 |
| --- | --- |
| 퀵 정렬이 작은 쪽만이 아니라 **양쪽을 모두 재귀**하게 | 검사 **1개** 실패 — "최악에도 깊이 log₂ n 이하". 정렬 결과는 맞으므로 이 검사가 없으면 모른다 |
| `merge`에서 R을 `arr[mid + 1 + j]` 대신 `arr[mid + j]`로 복사 | 검사 **7개** 실패 |
| 분할 조건 `arr[j] < pivot` → `<=` | 실패 없음. 버그가 아니라 같은 값을 반대쪽으로 보낼 뿐이고, "모두 같은 값"이 O(n²)인 것도 같다 |

C와 Python을 같은 알고리즘으로 맞춘 것은 저장소 규약("두 구현이 같은 결과를 내야 한다")
때문이다. 예제 배열 `6 2 5 1 7 3 4`에서 두 구현 모두 병합 14번 · 퀵 12번 비교, 보고 정렬
2,190번 섞기로 똑같이 나온다(`make demo`).

## 2. 알고리즘 상세

세 정렬이 실제로 어떻게 도는지. 예시는 배열이 한 걸음마다 어떻게 바뀌는지를 따라간다.

### 2.1 병합 정렬

배열을 반으로 나눠 각각 정렬한 뒤, 정렬된 두 반쪽을 병합한다.

```text
[6 2 5 1 7 3 4]
[6 2 5 1]      [7 3 4]        ← mid = left + (right - left) / 2 에서 나눈다
[1 2 5 6]      [3 4 7]        ← 각각 재귀로 정렬
[1 2 3 4 5 6 7]               ← L, R의 앞머리끼리 비교해 작은 쪽을 arr에 채운다
```

핵심은 병합 조건이 `L[i] <= R[j]`라는 것이다. **같은 값이면 왼쪽을 먼저 내보내므로** 같은
값의 원래 순서가 유지되는 안정 정렬이 된다.

```c
while (i < n1 && j < n2) {
    if (L[i] <= R[j]) arr[k++] = L[i++];   /* '<' 이면 불안정해진다 */
    else arr[k++] = R[j++];
}
```

- 입력 모양과 관계없이 항상 반으로 나누므로 깊이는 ⌈log₂ n⌉, 비교는 최악에도 O(n log n)이다.
- 대가는 임시 배열이다. `merge`가 매번 L, R을 새로 만들고, 가장 클 때는 마지막 병합에서 n칸이다.
- 이미 정렬된 입력에서는 병합할 때 L이 먼저 바닥나 비교가 절반 가까이 준다.

### 2.2 퀵 정렬

피벗을 하나 골라 **피벗보다 작은 값 / 피벗 / 나머지**로 나눈 뒤 양쪽을 정렬한다. Java 코드와
같이 피벗을 **무작위로** 골라 맨 뒤로 보낸 다음 Lomuto 방식으로 나눈다.

```text
[6 2 5 1 7 3 4]      무작위로 고른 피벗이 4라고 하자 (맨 뒤로 보냄), i = -1
 6 < 4 ? 아니오
 2 < 4 ? 예 → i=0, 교환   [2 6 5 1 7 3 4]
 5 < 4 ? 아니오
 1 < 4 ? 예 → i=1, 교환   [2 1 5 6 7 3 4]
 7 < 4 ? 아니오
 3 < 4 ? 예 → i=2, 교환   [2 1 3 6 7 5 4]
 피벗을 i+1로             [2 1 3 | 4 | 7 5 6]
```

**Java 코드와 같이 작은 쪽만 재귀한다.** 교과서처럼 양쪽을 모두 재귀하면, 분할이 계속 한쪽으로
치우칠 때 재귀가 n단계까지 들어가 스택 오버플로가 난다. 작은 쪽만 재귀하고 큰 쪽은 반복문으로
처리하면 재귀할 때마다 구간이 절반 이하가 되므로 깊이가 log₂ n을 넘지 않는다.

```c
while (low < high) {
    int pi = partitionRandom(arr, low, high, rand);
    if (pi - low < high - pi) {             /* 왼쪽이 작다 */
        quickSort(arr, low, pi - 1, rand);  /* 작은 쪽만 재귀 */
        low = pi + 1;                       /* 큰 쪽은 반복 */
    } else {
        quickSort(arr, pi + 1, high, rand);
        high = pi - 1;
    }
}
```

- 추가 메모리가 없다(배열 안에서 교환). 멀리 떨어진 원소끼리 교환하므로 불안정 정렬이다.
- 피벗을 무작위로 고르므로 이미 정렬된 입력도 최악이 되지 않는다.
- **약점은 같은 값이다.** 피벗보다 **작은** 값만 왼쪽으로 보내므로, 모든 값이 같으면 왼쪽이
  항상 비고 구간이 한 칸씩만 줄어든다. 비교가 n(n-1)/2, 곧 O(n²)이 된다. 작은 쪽만 재귀하는
  처리는 이때 스택은 지켜 주지만(깊이 1) 시간은 줄이지 못한다.

### 2.3 보고 정렬 — AI로 학습한 내용

보고 정렬은 수업에서 다루지 않아 AI(Claude)에게 질문하며 공부했다. 참고 자료는 과제 공지의
Wikipedia 비교표(Sorting algorithm — Comparison of algorithms)와 Bogosort 문서다. 아래는
질문과 답을 정리한 것이고, 숫자로 확인할 수 있는 것은 [3.2절](#32-실험-결과)에서 직접 쟀다.

```text
while (배열이 정렬되어 있지 않다)
    배열을 무작위로 섞는다      // Fisher-Yates 셔플
```

예를 들어 `[3 1 4 2]`는 이 저장소의 씨앗으로 15번을 섞은 뒤에야 `[1 2 3 4]`가 되었다.

**Q1. 보고 정렬은 어떤 정렬인가?**
배열이 정렬되어 있는지 확인하고, 아니면 전체를 무작위로 섞기를 정렬될 때까지 반복한다.
이름은 영어 *bogus*(엉터리의)에서 왔고 permutation sort, stupid sort, monkey sort라고도
부른다. 원숭이가 타자기를 무작위로 치다 보면 언젠가 셰익스피어를 쓴다는 "무한 원숭이 정리"와
같은 발상이다.

**Q2. "무작위로 섞기"는 어떻게 구현하나?**
Fisher-Yates 셔플을 쓴다. 뒤에서부터 i번째 원소를 0 ~ i 중 무작위 위치의 원소와 바꾼다. 이래야
n!가지 순서가 모두 같은 확률로 나온다. 매번 0 ~ n-1 중에서 고르면 순서마다 확률이 달라진다.

**Q3. 시간 복잡도는?**
서로 다른 원소 n개를 한 번 섞어 정렬될 확률은 1/n!이다. 성공할 때까지 반복하는 횟수는
기하분포를 따르고 기댓값이 n!이다. 한 번 섞는 데 O(n)이므로 평균 O(n · n!)이다.

| 경우 | 시간 | 설명 |
| --- | --- | --- |
| 최선 | O(n) | 이미 정렬된 입력. 확인(비교 n-1번)만 하고 끝난다 |
| 평균 | O(n · n!) | 기대 섞기 n!번 × 한 번에 O(n) |
| 최악 | 상한 없음 | 난수가 계속 틀리면 끝나지 않을 수 있다 (확률은 0에 수렴) |

**Q4. 정렬 확인도 매번 n-1번 비교하나?**
아니다. 처음으로 어긋난 이웃에서 멈춘다. 무작위 순서에서 앞의 k쌍이 모두 올바를 확률은
1/(k+1)!이므로 확인 한 번의 평균 비교는 1/1! + 1/2! + 1/3! + … ≈ **e − 1 ≈ 1.718번**이다.
그래서 보고 정렬의 시간은 비교보다 섞기가 대부분을 차지한다.

**Q5. 끝나지 않을 수도 있는데 알고리즘이라 할 수 있나?**
무작위 보고 정렬은 **라스베이거스 알고리즘**이다. 결과는 항상 맞지만 걸리는 시간이 확률적이다.
반대로 몬테카를로 알고리즘은 시간은 정해져 있지만 답이 틀릴 수 있다. 순열을 차례로 전부
시도하는 결정적 버전은 최악에도 n!개 안에서 반드시 끝난다.

**Q6. 메모리와 안정성은?**
배열 안에서 섞기만 하므로 추가 메모리는 O(1)이다. 같은 값들이 어떤 순서로 멈출지는 우연이므로
불안정하다. 같은 값이 있으면 정렬된 배치가 여러 개라 더 빨리 끝난다.

**Q7. 쓰이지 않는 정렬을 왜 배우나?**
나쁜 알고리즘이 얼마나 나쁠 수 있는지의 기준이 되고, 무작위 알고리즘의 기댓값 계산을 연습하기
좋다. "답을 확인하는 것(O(n))은 쉬워도 답을 찾는 것은 어렵다"는 점을 극단적으로 보여 준다.

## 3. 알고리즘 실험

같은 잣대로 재고 견준 결과.

### 3.1 실험 개요

#### 무엇을 어떻게 쟀나

```text
main.c ── 크기 n × 입력 종류마다 ──┐
                                  ├─ generateXxx(n)로 입력 base를 만든다 (씨앗 고정)
                                  ├─ base를 a, b, c로 복사
                                  ├─ sortStatsReset → clock 시작 → mergeSort(a) → clock 끝 → 출력
                                  ├─ sortStatsReset → clock 시작 → quickSort(b) → clock 끝 → 출력
                                  └─ n ≤ 10이면 bogoSort(c), 아니면 skipped
```

| 재는 것 | 방법 | 주의 |
| --- | --- | --- |
| 시간 | `clock()`, 복사는 빼고 정렬만, 1회 | 기계 · 부하에 흔들린다. 0.01 ms 이하는 믿기 어렵다 |
| 비교 횟수 | 원소끼리 비교할 때마다 센다 | 씨앗이 고정이라 **언제 돌려도 같다.** 보고서는 이쪽을 근거로 쓴다 |
| 메모리 | `merge`가 잡은 임시 배열의 최대 바이트 | 재귀 스택은 세지 않는다 |
| 재귀 깊이 | 실제로 들어간 최대 깊이 | 스택 사용량의 대리 지표 |
| 섞기 횟수 | 보고 정렬이 섞은 횟수 | 보고 정렬만 |

입력은 Java 코드와 같은 여섯 가지다: Random(0 ~ 999,999 무작위), Sorted, ReverseSorted,
NearlySorted(정렬된 배열에서 n/20번만 교환), FewUnique(0 ~ 4 다섯 가지 값), AllEqual(모두 42).

#### 안정성은 어떻게 다뤘나

Java 코드와 같이 `int` 배열을 정렬하므로 같은 값끼리 구별할 수 없어 안정성은 재지 못했다.
대신 코드로 판단했다. 병합 정렬은 `L[i] <= R[j]`로 같은 값에서 왼쪽을 먼저 내보내므로 안정하고,
퀵 정렬은 멀리 떨어진 원소를 교환하므로, 보고 정렬은 무작위로 섞으므로 불안정하다.

### 3.3 한계

- **시간은 한 기계에서 한 번 잰 값이다.** 작은 n에서는 `clock()`의 해상도보다 짧아 믿기 어렵다.
  비교 횟수를 함께 싣는 이유다.
- **안정성은 재지 못했다.** Java 코드와 같이 `int` 배열을 쓰므로 같은 값을 구별할 수 없다.
  (key, 입력 순서) 두 칸짜리 원소로 바꾸면 잴 수 있다.
- **퀵 정렬의 중복 약점은 고치지 않았다.** 피벗과 같은 값을 따로 모으는 3-way 분할을 쓰면
  AllEqual이 O(n)이 된다. 이번에는 Java 코드와 같은 분할을 비교하기 위해 그대로 두었다.
- **보고 정렬은 10번 평균이다.** 섞기 횟수의 흔들림이 커서(n = 6에서 n!의 0.65배, n = 5에서
  1.6배) 회차를 늘리면 n!에 더 가까워질 것이다.
- **재귀 스택은 메모리에 세지 않았다.** 대신 재귀 깊이를 따로 실었다.
