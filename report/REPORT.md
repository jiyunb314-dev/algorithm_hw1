# 고급알고리즘 1차 과제 — 정렬 알고리즘 비교

<p align="right">배지윤 (2026193117)</p>

- 비교한 정렬: 병합 정렬, 퀵 정렬(수업에서 배운 정렬), 보고 정렬(bogosort, 배우지 않은 정렬)
- GitHub 저장소: <https://github.com/jiyunb314-dev/algorithm_hw1>

## 개요

병합 정렬, 퀵 정렬, 보고 정렬을 C로 구현하고, 배열 크기(10, 100, 1,000, 10,000, 50,000,
100,000)와 입력 종류(무작위, 정렬됨, 역순, 거의 정렬됨, 적은 종류의 값, 모두 같은 값)를
조합한 36가지 조건에서 비교하였다. 조건마다 같은 입력을 복사해 세 정렬에 넘기고, 걸린
시간(ms), 임시 배열 메모리(MB), 비교 횟수, 재귀 깊이를 기록하였다. 보고 정렬은 평균 n!번을
섞어야 하므로 n = 10에서만 돌리고 그보다 큰 배열은 건너뛰었다.

코드의 흐름은 참고한 Java 코드(`Algorithms.java`)를 따랐다.

| Java | C (이 저장소) | 역할 |
| --- | --- | --- |
| `merge`, `mergeSort(arr, left, right)` | `merge`, `mergeSort` (`src/sort.c`) | L, R 임시 배열로 병합 |
| `partitionRandom`, `quickSort(arr, low, high, rand)` | `partitionRandom`, `quickSort` (`src/sort.c`) | 무작위 피벗, 작은 쪽만 재귀 |
| (없음) | `isSorted`, `shuffle`, `bogoSort` (`src/sort.c`) | 보고 정렬 |
| `generateRandom` 등 6개 | 같은 이름 6개 (`src/data.c`) | 실험 입력 생성 |
| `main`의 크기 × 입력 반복 | `main.c`의 `experiment()` | 실험과 출력 |

`java.util.Random` 대신 xorshift 난수를 직접 구현해 씨앗을 고정했다. 그래서 몇 번을
돌려도 같은 입력이 나오고, 비교 횟수 같은 값은 매번 똑같이 재현된다. 같은 세 정렬을
Python(`src/sort.py`)으로도 구현하여 C와 비교 · 섞기 횟수까지 같은 결과가 나오는지
테스트로 확인하였다(`make test`, C 34개 · Python 6개 검사 통과).

## 결과 분석

### 병합 정렬

병합 정렬은 모든 배열 크기와 입력 종류에서 가장 고른 성능을 보였다. 100,000개 기준으로
입력 종류에 관계없이 4.9 ~ 13.3 ms 안에 끝났다. 무작위 입력에서 배열 크기가 10,000에서
100,000으로 10배가 되자 비교 횟수는 약 12.7배 늘었는데, n log n으로 계산한 증가율(약 13.3배)과
비슷해 O(n log n)대로 자란다는 것을 확인했다. 무작위 100,000개에서 비교 횟수는 1,536,246번으로
n log₂ n(약 166만)과 거의 같았다.

항상 배열을 절반으로 나누기 때문에 재귀 깊이도 입력과 관계없이 17(= ⌈log₂ 100,000⌉)로
일정했다. 이미 정렬된 입력이나 모두 같은 값에서는 병합할 때 한쪽이 먼저 끝나 비교가 절반
가까이(853,904번) 줄어 오히려 더 빨랐다. 어떤 입력에서도 느려지는 경우가 없었다는 점에서
가장 안정적이고 예측 가능한 알고리즘이었다.

### 퀵 정렬

퀵 정렬은 무작위, 정렬됨, 역순, 거의 정렬된 입력에서 가장 빨랐다. 100,000개 무작위 입력에서
8.5 ms로 병합 정렬(13.3 ms)보다 약 1.5배 빨랐다. 비교 횟수는 오히려 병합 정렬보다
많았지만(194만 번 대 154만 번), 임시 배열을 만들고 복사하는 작업이 없어서 실제 시간은 더
짧았다. 피벗을 무작위로 고르기 때문에 이미 정렬된 입력에서도 최악의 경우가 생기지 않았다.

그러나 같은 값이 많은 입력에서는 성능이 크게 무너졌다. 100,000개 기준으로 "적은 종류의 값"
(0 ~ 4)에서 538 ms, "모두 같은 값"에서 2,882 ms가 걸려 병합 정렬(각각 7.4 ms, 5.1 ms)보다
73배, 570배 느렸다. 참고한 Java 실험에서도 "모두 같은 값" 100,000개가 2,000 ms 이상 걸렸는데,
같은 현상이 C에서도 재현된 것이다.

원인은 분할 방식에 있다. `partitionRandom`은 피벗보다 **작은** 값만 왼쪽으로 보내므로,
모든 값이 같으면 왼쪽이 항상 비고 구간이 한 칸씩만 줄어든다. 그래서 비교 횟수가 정확히
n(n-1)/2 = 4,999,950,000번이 되었다. 값이 다섯 종류뿐일 때도 같은 값끼리 모인 약 20,000개짜리
덩어리마다 같은 일이 일어나 비교가 약 10억 번이 되었다. 피벗을 무작위로 골라도 값 자체가
같으면 소용이 없다는 것을 확인했다.

한편 재귀 깊이는 모든 경우에 11 이하였고, "모두 같은 값"에서는 1이었다. Java 코드의 주석처럼
두 쪽 중 **작은 쪽만 재귀하고 큰 쪽은 반복문으로** 처리했기 때문이다. 이 처리가 없었다면
"모두 같은 값"에서 재귀가 100,000단계까지 들어가 스택 오버플로가 났을 것이다. 다만 이 방법은
스택만 지켜 줄 뿐 O(n²)인 시간 자체는 줄이지 못한다.

### 보고 정렬

보고 정렬은 원소 10개짜리 무작위 배열을 정렬하는 데 2,315,638번을 섞었고 87.5 ms가 걸렸다.
같은 배열을 병합 정렬과 퀵 정렬은 20여 번의 비교, 0.002 ms 안에 끝냈다. 원소 10개에서 이미
퀵 정렬의 100,000개 무작위 입력(8.5 ms)보다 10배 느린 것이다.

입력에 따라 결과가 극단적으로 갈렸다. 정렬됨, 거의 정렬됨(n = 10이면 교환 횟수 n/20 = 0),
모두 같은 값에서는 한 번도 섞지 않고 비교 9번(n - 1)으로 바로 끝났다. 역순은 1,033,033번,
값이 다섯 종류뿐인 입력은 138,524번을 섞었다. 같은 값이 많으면 정렬된 순서로 인정되는 배치가
여러 개라 빨리 끝난다.

n을 1부터 10까지 늘려 가며 10번씩 돌린 결과, 평균 섞기 횟수가 n!과 거의 같았다
(n = 8: 39,991번 대 8! = 40,320, n = 9: 357,875번 대 9! = 362,880). 한 번 섞는 데 약 40 ns가
들었으므로 이 속도라면 n = 12는 약 20초, n = 15는 반나절 이상, n = 20은 수천 년이 걸린다.
그래서 n > 10은 실행하지 않았다(Java 코드가 삽입 정렬을 10,000개보다 큰 배열에서 건너뛴 것과
같은 방식).

### 메모리 사용량

병합 정렬만 추가 메모리를 사용했다. `merge`가 매번 L, R 임시 배열을 만들기 때문이며, 가장
클 때가 마지막 병합에서 배열 전체(n칸)를 복사할 때다. 100,000개에서 0.38 MB(= 100,000 × 4바이트)로,
참고한 Java 실험(1 ~ 4 MB)보다 작은 것은 C가 가비지 컬렉터 없이 필요한 만큼만 잡고 바로
해제하기 때문이다. 퀵 정렬과 보고 정렬은 배열 안에서 교환만 하므로 임시 배열이 0 MB였다.
퀵 정렬은 대신 재귀 스택을 쓰지만 깊이가 11 이하라 무시할 만했다. 병합 정렬은 크기에 비례하는
적은 메모리를 더 써서 어떤 입력에서도 느려지지 않는 성능을 얻는다고 정리할 수 있다.

## 배우지 않은 정렬: 보고 정렬 (AI로 학습한 내용)

보고 정렬은 수업에서 다루지 않아 AI(Claude)에게 질문하며 공부하였다. 참고 자료는 과제
공지의 Wikipedia 비교표(Sorting algorithm — Comparison of algorithms)와 Bogosort 문서다.
아래는 질문과 답변을 정리한 것이다.

**Q1. 보고 정렬은 어떤 정렬인가?**
배열이 정렬되어 있는지 확인하고, 아니면 배열 전체를 무작위로 섞는 과정을 정렬될 때까지
반복한다. 이름은 영어 *bogus*(엉터리의)에서 왔고 permutation sort, stupid sort, monkey sort라고도
부른다. 원숭이가 타자기를 무작위로 치다 보면 언젠가 셰익스피어를 쓴다는 "무한 원숭이 정리"와
같은 발상이다.

```text
while (배열이 정렬되어 있지 않다)
    배열을 무작위로 섞는다      // Fisher-Yates 셔플
```

**Q2. "무작위로 섞기"는 어떻게 구현하나?**
Fisher-Yates 셔플을 쓴다. 뒤에서부터 i번째 원소를 0 ~ i 중 무작위 위치의 원소와 바꾼다. 이렇게
해야 n!가지 순서가 모두 같은 확률로 나온다. 매번 0 ~ n-1 중에서 고르면 순서마다 확률이 달라진다.

**Q3. 시간 복잡도는?**
서로 다른 원소 n개를 한 번 섞어 정렬된 순서가 나올 확률은 1/n!이다. 성공할 때까지 반복하는
횟수는 기하분포를 따르고 기댓값이 1/(1/n!) = n!이다. 한 번 섞는 데 O(n)이 들므로 평균은
O(n · n!)이다. 이미 정렬된 입력은 확인만 하고 끝나므로 최선은 O(n)이다. 최악은 상한이 없다.
난수가 계속 틀리면 끝나지 않을 수도 있기 때문이다(그 확률은 0에 수렴한다).

**Q4. 정렬 확인도 매번 n - 1번 비교하나?**
아니다. 처음으로 어긋난 이웃에서 멈춘다. 무작위 순서에서 앞의 k쌍이 모두 올바를 확률은
1/(k+1)!이므로, 확인 한 번의 평균 비교 횟수는 1/1! + 1/2! + 1/3! + … ≈ e − 1 ≈ 1.718번이다.
그래서 보고 정렬의 시간은 비교보다 섞는 작업이 대부분을 차지한다.

**Q5. 끝나지 않을 수도 있는데 알고리즘이라 할 수 있나?**
무작위 보고 정렬은 **라스베이거스 알고리즘**이다. 결과는 항상 맞지만 걸리는 시간이 확률적이다.
반대로 몬테카를로 알고리즘은 시간은 정해져 있지만 답이 틀릴 수 있다. 순열을 하나씩 차례로
전부 시도하는 결정적 버전도 있는데, 이것은 최악에도 n!개 안에서 반드시 끝난다.

**Q6. 공간 복잡도와 안정성은?**
배열 안에서 섞기만 하므로 추가 메모리는 O(1)이다. 같은 값들이 섞인 뒤 어떤 순서로 멈출지는
우연이므로 불안정 정렬이다. 같은 값이 있으면 정렬된 배치가 여러 개가 되어 더 빨리 끝난다.

**Q7. 실제로 쓰이지 않는 정렬을 왜 배우나?**
나쁜 알고리즘이 얼마나 나쁠 수 있는지 보여 주는 기준이 되고, 무작위 알고리즘의 기댓값을 계산해
보는 연습이 된다. 또 "답이 맞는지 확인하는 것(O(n))은 쉬워도 답을 찾는 것은 어렵다"는 점을
극단적으로 보여 준다.

**AI의 설명을 실험으로 확인한 결과**

| AI의 설명 | 측정 결과 | 일치 |
| --- | --- | --- |
| 평균 섞기 횟수는 n! | n = 8: 39,991번 (8! = 40,320), n = 9: 357,875번 (9! = 362,880), n = 10: 4,084,984번 (10! = 3,628,800) | 일치 |
| 확인 한 번에 평균 약 1.718번 비교 | 비교 횟수 ÷ 섞기 횟수 = 1.718 (n = 9, 10) | 일치 |
| 최선의 경우 O(n) | 정렬된 입력 n = 10: 섞기 0번, 비교 9번 | 일치 |
| 같은 값이 많으면 빨리 끝남 | n = 10 무작위 2,315,638번, 값 다섯 종류 138,524번 | 일치 |
| 걸리는 시간이 확률적 | n = 10, 10번 실행: 최소 232,310번 ~ 최대 12,515,749번 (54배 차이) | 일치 |

평균 비교 횟수가 e − 1이라는 설명은 처음에는 믿기 어려웠는데, 측정값이 소수점 셋째 자리까지
1.718로 나오는 것을 보고 이해할 수 있었다.

## 나의 의견

이번 실험에서 가장 인상 깊었던 알고리즘은 퀵 정렬이다. 같은 알고리즘이 무작위 입력에서는
세 정렬 중 가장 빨랐는데, 모든 값이 같은 입력에서는 병합 정렬보다 570배나 느렸다. 코드에서
`arr[j] < pivot`이라는 비교 한 줄이 같은 값을 모두 한쪽으로 몰아 이런 차이를 만든다는 것이
흥미로웠다. 피벗과 같은 값을 따로 모으는 3-way 분할을 쓰면 이 문제가 해결된다고 하니 다음에
직접 구현해 비교해 보고 싶다.

실제로 정렬 알고리즘 하나를 골라 써야 한다면 병합 정렬을 고르겠다. 평균 속도는 퀵 정렬보다
조금 느리지만, 어떤 입력이 들어와도 O(n log n)을 벗어나지 않는다는 점이 더 중요하다고 생각한다.
추가 메모리도 100,000개에서 0.38 MB로 부담이 크지 않았다.

## 배운 점

첫째, 평균 시간 복잡도가 같아도 입력에 따라 실제 성능은 크게 달라진다는 것을 배웠다. 퀵 정렬과
병합 정렬은 둘 다 평균 O(n log n)이지만, 같은 값이 많은 입력에서는 수백 배 차이가 났다. 정렬을
고를 때는 평균뿐 아니라 최악의 경우와 실제 데이터의 모양을 함께 봐야 한다.

둘째, 스택 오버플로를 막는 방법과 시간을 줄이는 방법은 별개라는 것을 알게 되었다. 작은 쪽만
재귀하는 퀵 정렬은 재귀 깊이를 11 이하로 지켰지만, 2,882 ms라는 시간은 그대로였다.

셋째, 보고 정렬을 통해 n!이 얼마나 빨리 커지는지 체감했다. 원소 10개에 이미 수백만 번을 섞어야
했고, 20개면 수천 년이 걸린다. O(n log n)과 O(n · n!)의 차이는 "조금 느리다"가 아니라
"끝나느냐 마느냐"의 차이였다.

넷째, AI에게 배운 내용을 그대로 믿지 않고 직접 실험으로 확인하는 과정이 공부에 도움이 되었다.
기댓값 n!과 e − 1 같은 숫자를 측정값과 맞춰 보면서 설명을 더 확실히 이해할 수 있었다.
